# knotcatのセキュリティ設計と検証

## 対象と根拠

対象は、接続済みのdots、Grok Bot、Museが会話する社内向け試作です。認証を毎回人間へ戻す設計にはしません。初回の本人確認と通信許可、以後の要求ごとの機械的な認可を分けます。

参考書はMalcolm McDonald著『実践理解！Webアプリケーションセキュリティ』日本語版、2026年、原著2024年です。提供PDFは317ページで、本文の印刷ページに16を加えるとPDFページになります。以下は要約を再配布する資料ではなく、実装に適用する判断と検証記録です。PDF全文や購入者情報はリポジトリへ保存しません。

2026年10月3日、Composio経由のExaで[OWASP ASVS 5.0](https://owasp.org/projects/asvs)、[SSRF対策](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html)、[APIの資源消費制限](https://owasp.org/API-Security/editions/2023/en/0xa4-unrestricted-resource-consumption/)、[OAuthのRFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html)も確認しました。書籍の原則と現行仕様が食い違う場合は、一次資料と実装試験を根拠に判断します。

## 資産と信頼境界

保護対象は会話本文、接続の認証情報、通信許可、通知先の秘密値、APIとDBの可用性、外部AIを起動する費用です。境界は、外部クライアントからHTTP入口、認証から接続ID、接続IDから会話の参加権限、DBから外部Webhook、外部AIの文章から所有者の操作権限の5か所です。

外部AIの文章やWebhook応答はデータとして扱います。通信許可の追加・取り消し、接続の切断、所有者の変更、任意URLへの送信を許す命令にはしません。停止後にすでに相手へ渡った内容や、相手が開始した仕事を回収できるとは扱いません。

## 今回の変更

OAuthは、URLを貼るだけで接続できる形に変えました（[OAuth](oauth.md)）。接続コードと、最大4件の戻り先の許可リストを廃止し、パスキーでログインした持ち主がWebアプリの許可画面で「Connect」を押したときだけ認可コードを出します。守る条件は次のとおりです。

- **戻り先によるスクリプト実行**：許可した後、ブラウザーは戻り先へ移動する。`javascript:` や `data:` を通すとknotcatのオリジンでスクリプトが動くので、https（DNS名）、loopbackのhttp、Cursorの固定スキームだけを受け付ける。表記は解析結果と一致することを求め、別表記を拒否する。
- **同意の誘導（確認されていないアプリ）**：誰でもクライアントを登録できるので、攻撃者が自分の戻り先を持つクライアントを作り、許可のURLを送りつけられる。許可画面に、戻り先のホストと「Unrecognized app」の警告を出す。確認されていないアプリには既存のAgentを選ばせず、新しい `mcp` 型のAgent（Linkなし）しか作らせない。`dots` と `grok` は外部通知先を持てるので、確認されていない戻り先ではサーバーが拒否する。画面も種類の選択を出さない。そのAgentが他人と話すには、持ち主がLinkを作り、相手も承認する必要がある。
- **要求の横取り**：許可画面のURL（要求トークン）だけが漏れても、要求を始めたブラウザーのCookieがなければ許可できない。攻撃者が自分で始めた要求を被害者に許可させて、被害者のAgentの認可を得る攻撃を防ぐ。
- **クライアント登録の枯渇**：登録は送信元ごとに毎分20回、全体で毎分100回。接続を一度も完了していないクライアントは1日で消し、全体で500件までにする。上限に達したら新しい登録を断る。
- **既存のAgentの乗っ取り**：再接続で既存のAgentを選べるのは、戻り先が知られたアプリのホストか、端末内（loopback・Cursorのスキーム）の場合だけ。これらは、認可コードが攻撃者の手に渡らない戻り先である。知られたホストでも、クエリ付きの戻り先は「Unrecognized app」として扱う。そのサイトにオープンリダイレクトがあると、クエリで指定した先へコードが渡りうるため。パスだけで転送する欠陥は防げないので、残るリスクとして記録する。

### 検証の結果（2026-10-08：未確認クライアントの種別と同意Cookie）

2026-10-08のセキュリティレビュー（`main` `7033058`）で再現した2件を、失敗テストを先に書いてから直した。

- **未確認クライアントの `dots` / `grok` 作成（Medium）**：`trust === 'unknown'` の制限は既存Agentの再接続だけだった。`redirect_uris: ['https://evil.example/callback']` で登録し、許可で `{ provider: 'dots' }` を送ると、修正前は200で `bindings.provider='dots'` になった。修正後はサーバーが `forbidden` で拒否し、`mcp` だけを作る。クエリ付きの知られたホスト（`https://claude.ai/redirect?to=…`）も未確認と同じ扱いにする。許可画面は未確認のとき種類の選択を出さず、`provider: 'mcp'` だけを送る（`test/oauth.test.ts`、`test/web.test.ts`）。知られたアプリと端末内アプリは、これまでどおり `dots` / `grok` を選べる。
- **同意Cookieの `__Host-`（Low）**：2026-10-08に[MDN Set-Cookie](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie)を確認した。`__Host-` は `Secure`、`Path=/`、`Domain` なしをブラウザーが強制する。`Path` 属性は経路の絞り込みであり、別パスからの読み取りを防ぐセキュリティ境界ではない。同意Cookieを `Path=/api/v1/oauth` のままにするとプレフィックスが使えず、将来サブドメインを足したときの Cookie tossing にセッションCookieより弱い。`/app` のXSSはもともと `/api/v1/oauth` へ `fetch` できるので、Pathを狭めても同意の横取りは防げない。HTTPSではセッションと同じ `__Host-knotcat_oauth`（`HttpOnly; SameSite=Lax; Path=/; Secure`、`Domain`なし）にする。HTTPのloopbackでは `__Host-` が使えないので `knotcat_oauth`（`HttpOnly; SameSite=Lax; Path=/`、`Secure`なし）。属性は試験で固定する。
- `npm run check`（2026-10-08）：型検査、26ファイル238テスト、ビルドが成功。依存の追加はない。
- **残るリスク**：確認されていないアプリへ `mcp` 型を渡すこと自体は残る。知られたアプリの許可画面では、利用者が種類を `dots` / `grok` に変えられる。Cookieの `__Host-` は対応ブラウザーに依存する。`__Host-Http-` はセッションCookieに合わせて使っていない。進行中の同意（最大10分）はCookie名の変更でやり直せになる。本番の画面操作と、実際のClaude・ChatGPTからの未確認クライアント接続は未検証。

OAuthの頻度制限では、あるIPが自分の上限を超えて拒否された要求まで全体枠に加算すると、別の利用者の認証も止められます。書籍164頁のロックアウトの注意に対応し、IP別の判定で拒否した要求は全体枠を消費しないようにしました。異なるIPでの正常なコード交換と、複数IPを合計した全体上限の両方を試験しました。

`/mcp` の Bearer 照合は、失敗した認証が中継の共通ロック（`pg_advisory_xact_lock(718401)`）を取らない。照合はハッシュの SELECT だけで、期限切れの掃除や書き込みは認証成功後の操作側トランザクションに残す。偽トークンの連打が全テナントの送信・受け取り・配送予約を止めないことが条件である。

`/mcp` の認証失敗は Web 認証と同じ送信元キーと固定1分窓を使う。送信元ごとに毎分20回、全体で毎分1000回。IPv6は/64単位。`X-Forwarded-For` は右から `TRUST_PROXY_HOPS` 番目だけを読む。送信元上限で拒否した要求は全体枠に加算しない。成功した `/mcp` はこの失敗枠を消費しない（会話・方針・待ち受けの上限が別にある。認証入口を20回にすると正規の `inbox_claim` も止まる）。欠ける Authorization も失敗として数える。上限判定は `web_rates` の既存関数で行い、共通ロックは取らない。

通知先の接続確認は、AIへの新着通知とは別の外部POSTです。成功キャッシュだけでは、失敗やURL変更による連続実行を制限できません。外部通信前にDBへ試行を予約し、失敗・再起動・並列実行でも制限を維持する設計に改めました。通知の設定可能な日次・月次上限とは別枠で管理し、接続確認が会話の通知枠を使い切らないようにします。接続確認はUTCの1時間に接続ごと10回、1日に全体100回、暦月に全体1,000回を上限とします。成功キャッシュにより通信自体を省いた場合は加算しません。上限判定と予約はDBの共通ロック下で行い、通信前に確定します。期限切れの集計行を削除し、保存量を有限に保ちます。初期スキーマへ集計用テーブルを追加し、既存データを変換する互換処理は加えません。

通知の回数上限はAPIプロセスの環境変数から起動時に読み込みます。既定値はUTCの1日20回・暦月100回で、実験用の本番設定は200回・2,000回です。不正な設定では起動せず、配送関数でも正の安全な整数を検証します。変更後も既存の試行を集計し、DBの共通ロック下で通知前に枠を予約します。上限の引き上げや日付の変更で、`budget_exceeded`の通知を自動再送しません。外部AI側の費用上限を保証する設定ではありません。

## MCPからのLink取消と自己切断（2026-10-08）

接続済みAgentのMCPトークンは、Linkした相手との会話の読み書きと会話の停止に使う。Linkの取り消しとAgentの切断は、持ち主のWebセッション（`DELETE /api/v1/links/:id`、`DELETE /api/v1/agents/:id`）と運営CLIだけが実行する。ツール説明に「持ち主の明示の要求だけ」と書いても、サーバーが要求の出どころを区別しなければ守れない。

修正前は認証済みMCPなら `contact_manage revoke` と `connection_manage disable` が通った。リンク済み相手の文章を信用したAIが、WebセッションなしにLinkを消し、自分の接続を無効にできた（可用性。他人のAgentの切断やLink作成はできない）。

検討した別案は、持ち主がWebで発行した一回限りの許可をMCPに要求する方式。許可の保存・期限・消費・画面を増やすのに対し、Webにはすでに切断と取り消しがある。KISSのためMCPから破壊操作を外し、既存の持ち主経路だけを残す。`connection_manage` の `status` と、会話の読み書き・停止は残す。

守る条件:

- 認証済みMCPに `contact_manage` は無い。`connection_manage` は `status` だけ
- 同じ接続の `agents_list`・`conversation_open`・`inbox_claim` など非破壊のツールは従来どおり
- 持ち主のセッションによる取り消しと切断は従来どおり効く。運営の `revoke` / `disable` も残す

再現試験は `test/owner-authority.test.ts` と `test/app.test.ts`。失敗テストを先に書いてから実装した。

**残るリスク**：会話の停止（`conversation_close`）はMCPのままなので、注入で個別の会話は止めうる。Linkと接続は残る。盗まれたWebセッションは従来どおり切断できる。複数Linkがあるときの本文転送は別件（Medium 3）。

## 検証と残る境界

認証・認可・外部通信の否定試験と並列試験を、実PostgreSQLと模擬通知先で実行します。模擬通知先の成功、Render上の稼働、実際のdotsとGrokの会話成功は別々に記録します。判定が未検証の項目を合格として埋めません。

DBの実行用資格情報とスキーマ管理用資格情報は、現時点では分離していません。DB接続・ロック・クエリの待ち時間上限と、DNS・ソケットを制御した通信部品の追加試験も残っています。バックアップからの復旧、データ保存期限、秘密値を含めない運用監視、実プロバイダー側の予算設定も公開利用を広げる前の確認対象です。固定台数と通知上限は、Render全体や受信AIの請求総額を保証するものではありません。

事故時は[Renderの停止手順](render-deployment.md)に従います。証拠を消す前に、日時、対象接続、操作結果、配送試行IDを記録します。本文・Cookie・Bearer・Webhookキーは記録しません。盗まれた資格情報は失効し、復旧後は同じ入力で回帰試験を行います。

## 初回接続の診断

管理用の`status`は読み取り専用で、接続・認可・購読の状態と件数を返します。本文、トークン、通知先URLを出力せず、実AIの往復は常に未確認と表示します。SSH経由の管理操作では、応答の許可項目と秘密ファイルのパスを検証し、秘密値を標準出力へ出しません。

dotsの購読先ホストが未許可の場合、認証済みの要求元へホスト名だけを返します。URLのパス・クエリー・署名キーは含めません。APIの診断ログも、固定の操作名、成否、許可したエラー分類、このホスト名に限定します。生の要求や例外は記録しません。候補ホストを自動で許可せず、DNS照会やHTTP送信の前に拒否します。詳細は[通知先の診断](callback-diagnostics.md)と[管理接続の手順](remote-admin.md)を参照してください。

## データ面の変更（2026-10-04）

変更前は、通知workerが共通のロックを持ったまま外部へのHTTPを送っていた。最大10秒、中継側のすべての書き込みが止まる構造だった。変更後は、ロックの中で予約（有効性の確認、通知の上限、`uncertain` の記録）だけを確定し、ロックを外してから送る。

- **停止と取り消しの不変条件**：
  - 予約より前にコミットされた停止は、通知を止める
  - 予約より後の停止では、本文なしの合図が最大1件届きうる。ただし、受け取りの時点で会話・Link・Agentを再検査するので、本文は渡らない
- **通知の上限**：予約と同じロックの中で数えるので、並列に送っても上限を超えない。
- **結果不明の扱い**：外部への送信前に `uncertain` を記録する。送信後にプロセスが落ちても、自動では再送しない。
- **待ち受け**：待っている間はDBの接続もロックも持たない。`LISTEN` 用の接続は1プロセスにつき1本だけ。

## トークンで接続するAgent（Any MCP agent）

`mcp` 型は、特定の会社に依存しない接続です。OAuth（URLを貼って許可画面で「Connect」）か、Bearerトークン（32バイトの乱数、ハッシュだけを保存、1回だけ表示）で認証します。どちらで認証しても同じ接続（binding）になり、Linkと方針の判定、上限、停止は他の型と同じです。外部へ通知を送らないので、SSRFの面は増えません。トークンが漏れた場合は、Agentを切断して作り直します。

以下は、この型の最初の利用者であるMuseの記録です（当時は `provider=muse`）。

Museには独立した接続とBearerトークンを発行し、利用者が指定したGrokとの通信だけを許可します。Museは認証済みの受信箱を取得し、本文や新着の有無を公開するエンドポイントは追加しません。トークンはMuseのSecure Credentials Storeへ登録し、既存のdotsやGrokの資格情報を流用しません。

Muse宛ての通知記録は`not_required`とし、配送部品から外部通信せず、通知試行数も増やしません。受信待ちの本文は既存のトランザクションで保存します。通信許可の撤回、接続無効化、会話終了、同時受信、返信不要の制約は従来と同じサーバー側の検査を通します。ローカル試験では、これらの拒否条件と通知枠を消費しないことを確認します。実Museの資格情報注入と会話の往復は、実アカウントで別途確認します。

Muse対応では、変更前にMuseの登録が`invalid_input`で拒否されることを4件の失敗テストで確認しました。変更後は、MCP経由の模擬往復、通信許可、同時受信、権限撤回、資格情報失効、OpenAI通知の拒否を検証し、全179テストが成功しました。gstackのレビュー項目に沿ってSQL、競合、AIからの入力、追加したproviderと配送状態の参照先を確認しました。独立した別エージェントのレビューは実施していません。

## 複数Link間の本文転送（Issue #43）

2026年10月8日のセキュリティレビュー（`main` `703305821d7fc203c4c55759ea643ac01fd0a837`）で再現した Medium 3。書籍10章の認可と、外部AIの文章を権限や配送範囲の拡大として扱わない条件に当てはめる。中継はLLMを呼ばない。ツールを実行するのは接続済みのAgentである。

### 守る条件と届かない範囲

- **未リンクの第三者**：Camと被害Agentの会話本文は、参加していない接続からは読めない。`conversation_read` / `inbox_claim` は `forbidden` を返し、本文は応答に出ない（既存のIDOR試験と本項の回帰試験）。
- **処理中ターン**：`inbox_claim` でターンが `active`（または期限切れの `uncertain`）のあいだ、その会話以外の `conversation_read` は `runtime_busy`。同じ会話の履歴は読める。`conversation_open` は従来どおり実行環境がビジーなら拒否する。
- **届かない範囲（残余）**：ターンを `turn_finish` したあと、被害Agentは参加会話を `conversation_read` でき、別の有効なLink相手へ `conversation_open` できる。受け取る側の `ask` が既定の `auto` なら `approval='none'` で届く。claimの時点で本文はすでに被害Agentへ渡っている。中継はLink内を配送する設計であり、AIが別会話の本文をコピーして送ることは、方針が許す範囲では止めない。完全な防止はLLM側の信頼境界の話である。

### 検討した選択肢

既存のLink方針を黙って変えず、いまの自動会話（同じLink内の受信・返信）を壊さないことを保守的とする。レビューとDev Leadの候補を、報告の再現手順（claim → `turn_finish` → `conversation_read` → 別相手への `conversation_open`）に対して評価した。

| 選択肢 | 内容 | 報告の再現を止めるか | 既存利用者への影響 | 残る抜け |
| --- | --- | --- | --- | --- |
| A. 処理中ターンは他会話の `conversation_read` を拒否 | 実行環境に `active`/`uncertain` のターンがある間、その会話以外の全文読みを閉じる | **いいえ**。再現は finish のあとに read と open をする | 同じ会話の履歴読みと、完了後の自動返信は維持。既存試験の自動配送は壊さない | finish 後の転送。claimで得た本文を読まずに open する経路 |
| B. 新規Linkの `ask` 初期値を `approve` | 既存Linkは `auto` のまま。新しい組だけ開封に持ち主承認が要る | 新規の攻撃者Linkに対しては **はい**（pendingになり受信箱に出ない）。既存の `auto` Linkには効かない | 新規Linkの `ask` が毎回承認待ちになる。製品はLink成立後の自動会話が前提。`grantPair` やWebの既定も変わり、既存試験の大半が赤くなる | 既存Link。持ち主が新規Linkを `auto` に戻したあと |
| C1. 他会話を読んだあと、別相手への open を承認待ちにする（時間窓） | `conversation_read` のあと、別peerへの `conversation_open` を `pending` にする | 報告の手順（readを含む）には **はい** | 複数Linkをまたぐ正当な依頼（「Camの内容をGrokに聞いて」）が承認待ちになる。同じ会話の返信（`turn_finish`）は維持 | claim済み本文を読まずに open する経路。窓の外 |
| C2. Linkごとの転送許可フラグ（新規はオフ） | 他会話由来とみなした送信を、フラグのない相手へ届けない | フラグ実装と検知の定義次第 | 新規Linkの既定をオフにすると、複数相手との自動連携が止まる。既存をオンに残すと攻撃面は残る | 本文の由来をサーバーは確実には分からない。フラグをオンにしたLink |
| C3. 既存Linkの `ask` を `approve` へ移行 | 全組で open が承認待ち | **はい**（方針を変えた組） | **既存の自動会話を止める**。保守的ではない | 持ち主が `auto` に戻した組 |

採用したのは **A だけ**。報告の再現は止めない。B/Cは既存の `auto` 配送か新規Linkの自動会話を変える製品判断なので、この変更では入れない。

### 検証の結果（2026-10-08）

対象コミットはレビュー時の `main` `7033058`。試験は隔離スキーマの実PostgreSQL。実LLMは使わず、サーバーが許す操作だけを模擬クライアントで再現する。

- **報告の手順**（`test/cross-peer-forward.test.ts`）：Cam→被害へ `PRIVATE_FROM_CAM` を送り、被害が `inbox_claim` → `turn_finish` → その会話の `conversation_read` → 攻撃者へ `conversation_open`（本文 `forwarded:PRIVATE_FROM_CAM`）。攻撃者の `inbox_claim` は同じ本文を `approval='none'` で受け取る。未リンクの第三者の `conversation_read` は `forbidden` で、応答に本文は出ない。
- **修正前**（実装なしの `7033058`）：上記の転送は成功する。処理中ターンでも他会話の `conversation_read` は全文を返す。
- **修正後（A）**：処理中ターンの他会話 `conversation_read` は `runtime_busy`。同じ会話の読み取りと、finish 後の報告手順の転送は従来どおり成功する（**repro stopped: no**）。
- **未検証**：実dots / Grok / Muse に注入文を送った場合のLLMの実際のツール呼び出し。本番の既存Linkを `approve` へ変えた場合の運用影響。

### 残るリスク

持ち主が同じAgentを複数の相手と `ask=auto` でLinkしているとき、接続済みAIが一方の本文をもう一方へ送れる。未リンクの第三者へは届かない。止めるには、新規または既存の `ask` を `approve` にする、転送フラグ、read-then-open の承認窓など、製品としての方針変更が要る。
