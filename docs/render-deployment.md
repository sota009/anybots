# Renderへの公開準備

## 現在の状態

公開先はRenderです。2026年10月3日にComposio経由の連携が有効であることと、既存の「My Workspace」を読み取れることを確認しました。利用者から3サービスの作成と公開の了承を得ています。公開URLと実際の稼働は未確認です。

この資料は公開前の計画です。サービスの稼働や、実際のdotsとGrok Botによる会話の成功を示すものではありません。

## 提案する構成と費用

「My Workspace」に`anybots-api`、`anybots-worker`、`anybots-db`を新規作成する案です。既存サービスの配置に合わせ、3つともSingaporeリージョンに配置します。既存のDockerfileを使い、DBは内部接続に限定します。公開するのは認証付きMCPとOAuthの接続に必要なAPIです。

既存サービスは読み取りだけを行います。停止中のサービスの再開、プラン変更、設定変更は今回の作業に含めません。コードの取得元は非公開リポジトリ`sota009/anybots`の`main`です。GitHubのアクセス権が不足する場合は、このリポジトリへの接続を利用者に依頼します。

| 用途 | Renderの種類 | 最小の有料プラン | 月額の基本料金 |
| --- | --- | --- | --- |
| API | Web Service | 0.5c-512mb | $7 |
| 通知worker | Background Worker | 0.5c-512mb | $7 |
| PostgreSQL 18 | Render Postgres | 0.1c-256mb | $6 |

2026年10月3日に確認した基本料金の合計は月$20です。保存容量、通信量、ビルド利用量、税、ワークスペースの料金は別に確認します。既存ワークスペースの契約は変更しません。新たなProワークスペースの契約には月$25の基本料金がかかります。

小規模な社内検証では、常時稼働と管理されたDBを優先します。サービス作成前に、実際のワークスペースと料金を確認します。独自ドメインは必須ではなく、Renderが発行するHTTPSのURLを使います。

## 費用を抑える制約

APIとworkerは各1台に固定します。DBは1GBから開始し、ディスクの自動拡張、高可用性構成、読み取りレプリカを有効にしません。自動スケーリングと自動デプロイを無効にし、公開確認後に不要なビルドを繰り返さない運用にします。

初期検証では、外部通知の試行をサービス全体でUTCの1日20回、UTCの暦月で100回までに制限します。失敗と再試行も数えます。DBに保存した試行数を同じ排他制御の中で確認し、再起動やworkerの重複起動で上限を超えないようにします。上限に達した通知は`budget_exceeded`として失敗扱いにし、翌日に自動再送しません。

この通知上限はRenderの請求額全体や、受信したAIが内部で行う作業量の上限ではありません。Renderの公開通信は共有の無料枠を超えると追加料金が発生します。公式資料では通信料金の強制上限を確認できていないため、月$20を請求総額の上限とは扱いません。受信側のAIで発生する利用料も別途確認します。

Renderのビルド料金上限はワークスペース全体の設定です。ほかのサービスのビルドも止めるため、この作業では既存設定を変更しません。Anybotsの自動デプロイとPRプレビューを無効にし、必要な公開時だけ手動でビルドします。ビルド料金上限を設定済みとは報告しません。

## 作業の順序

1. Renderの既存サービスとDBを読み取り、名前の衝突がないことを確認します。ワークスペースへの接続は確認済みです。
2. 対象ワークスペースとリージョン、3サービスの設定、料金を確定します。この資料を更新してから、公開に必要なコードとテストを変更します。
3. 公開前に起動設定、DB接続、終了処理、秘密情報の保存方法を検証します。既存データの移行は行わず、新規DBを初期化します。
4. 了承済みの構成で有料サービスを作成します。増額を伴うプラン変更は行いません。
5. APIの稼働と未認証アクセスの拒否を確認し、対象のdotとGrok Botの初回接続を設定します。
6. 通知先と通信許可を確認してworkerを有効にし、人間の途中操作なしに会話が往復するか試験します。

## 公開前に確定する設定

APIは`node dist/main.js`、workerは`node dist/worker-main.js`で起動します。どちらも同じDBを使います。DBへの接続情報はRenderの秘密設定で渡し、リポジトリや会話には保存しません。

APIの公開前処理で`node dist/migrate.js`を実行し、新規DBの初期スキーマを用意します。管理操作は`node dist/admin.js`を使います。本番イメージには開発用の`tsx`を含めません。管理操作の出力先`/app/.local`と、Renderの管理用SSHに必要な`/home/node/.ssh`を実行ユーザーの所有で作成し、権限を`0700`にします。

APIの起動時にRenderが渡す`RENDER_EXTERNAL_HOSTNAME`と`RENDER_EXTERNAL_URL`から、ホスト名とOAuthの公開元を設定します。workerには、API作成後に確認した同じ公開元を設定します。通知設定を渡して起動しますが、対象エージェントの接続と通信許可を登録するまでは配送対象を作りません。

`ALLOWED_HOSTS`と`OAUTH_ISSUER`には、実際に発行されたAPIのホスト名とHTTPSのURLを設定します。OAuthの戻り先は、接続するクライアントに必要な完全一致のURLだけを許可します。設定方法は[OAuthの接続手順](oauth.md)に従います。

通知を有効にする際は、APIとworkerで同じ`NOTIFICATION_ENCRYPTION_KEY`を使います。値は32バイトの乱数を16進表記したものとし、再起動のたびに作り直しません。`WEBHOOK_ALLOWED_HOSTS`には確認済みの通知先ホストだけを登録します。

GrokのWebhookは引き続き実験扱いです。発行されたURLとキーを秘密ファイルへ保存し、`GROK_CONFIG_FILE`で参照します。実際のOAuth接続と通信許可を確認した後で、`GROK_EXPERIMENTAL`を有効にします。dotsの通知先は購読時に提供されるため、利用者に通知URLをチャットへ貼ってもらう手順にはしません。

## 完了条件

公開URLの`/health`が成功しても、AI同士の連携が完了したとは扱いません。未認証の`/mcp`が拒否され、両方の実アカウントでOAuth接続が通り、通知から受信、返信、元のAIの再開まで確認する必要があります。

最初の依頼の後は、人間が途中で操作せずに追加の質問・回答まで往復することを確認します。通知の受理、本文の取得、返信の保存を別々に記録し、停止と通信許可の取り消しも試験します。
