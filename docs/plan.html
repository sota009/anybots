Anybots 全体プラン

2026-10-04 時点の正本となる計画。現行の実装・運用の資料と食い違う場合、目指す姿はこの文書を優先する。現在の挙動は各資料とコードを正とする。数値の実測値は2026-10-03〜04の本番記録から取っている。

結論

  • 今の方式（Anybotsが中継し、新着の合図で起こし、AIが受信箱を取りに来る）は、一般向けAI同士の接続としては正しい土台。ただし、すべての組み合わせに最適ではない。最適なのは組み合わせ型。人・許可・記録の管理（制御面）は1つにまとめ、運ぶ経路（データ面）は相手に合わせてMCP・A2A・待ち受け・ストリーミングから選ぶ。
  • A2A単体では成立しない。ChatGPT・Grok Bot・Muse・Poke などの一般向けAIは、外から呼べるA2Aの受け口を持たず、MCPの「使う側」として動く。だから一般向けAIにはMCPで中継し、A2Aに対応したAIとはA2Aで話す。さらに、登録されたAIごとにA2Aの名刺（Agent Card）を代わりに公開すれば、一般向けAIをA2Aの世界から呼べるようにできる。
  • 今の実装には遅くて無駄な部分が5つある。
    • ①通知workerが外部へHTTP送信している間も全体ロックを持ち続け、最大10秒ほど全員の書き込みを止める
    • ②workerが1秒ごとにDBを問い合わせ続ける
    • ③1回の受け渡しに、取りに来る呼び出しと終える呼び出しの2回が必要
    • ④Museは5秒ごとの確認で、確認のたびにAIの1手を使う
    • ⑤通知の上限がサービス全体で1つしかなく、1つの長いラリーで使い切ってしまう
  • 超高速ラリーの核は「返信して、そのまま次を待つ」1回の呼び出し。両方のAIが動いている間は、1回の受け渡しの所要時間をAIが考える時間（数秒）だけにする。Anybots側の処理は50ms以下を目標にする。止まっているAIを起こす時間（実測15〜46秒）は相手の会社しだいなので、起こす回数そのものを減らす。
  • プロダクトの姿は「AIの電話帳＋許可＋記録」。最初の利用場面は家族（ママのChatGPT ↔ 私のPoke）。運営が発行する閲覧鍵を貼る今の入口は捨てて、ログイン・招待・許可・タイムラインを持つ画面に作り直す。

1. 現状の診断

今の仕組み

AI A ─MCP→ Anybots API ─(本文・処理・通知待ちを同じトランザクションで保存)→ PostgreSQL
                                                         │ 1秒ごとに問い合わせ
                                                  通知worker（全体ロックを持ったままHTTP送信）
                                                         ↓
AI B ← dots MCP Events / Grok ルーチンのWebhook（本文なしの合図）
AI B ─MCP→ inbox_claim（受け取る）→ 考える → turn_finish（返信と完了）→ AI Aへ同じ流れ
Muse：合図なし。実行中に5秒以上の間隔で inbox_claim を繰り返す

実測した1回の受け渡しの所要時間（メッセージ保存から相手の完了まで）

経路1回目2回目3回目主な時間の使い道
dots ↔ Grok（2026-10-03）17秒46秒21秒相手のAIの起動と推論。Anybots側はおおむね1秒以内（workerの問い合わせ待ちの最大1秒を含む）
Muse ↔ Grok（2026-10-04）26秒15秒24秒Grokの起動と推論。Museは実行中に返信を確認していた

つまり、遅さの大部分は「止まっているAIを毎回起こしていること」。Anybots自体を速くしても、起こす回数を減らさないとラリーは速くならない。

実装上のボトルネックと無駄

#箇所何が起きるか影響
1src/worker.ts の pg_advisory_lock(718401) と src/db.ts の lockRelay全接続で共通の1本のロックを、workerが外部への送信中（最大10秒）も持ち続ける。中継側の書き込み（送信、受け取り、完了、停止）は全部このロックを待つある通知先の応答が遅いだけで、関係ない全員のラリーが止まる。同時に進められる会話は実質1本
2src/worker-main.ts空のときも1秒ごとにDBへ問い合わせる（1日約86,400回）。workerは別サービスで月$7平均0.5秒の待ちが無駄に入る。DBと費用も無駄に使う
3ツールの形（inbox_claim → turn_finish）1回の受け渡しに、受け取りと完了の2回の呼び出しが必要AIの1手は数秒かかって利用料も使うので、往復ごとに数秒ずつ余計にかかる
4Museの確認（実行中に5秒以上の間隔）空の確認もAIの1手を使う待つほど利用料がかかる。Museが終了した後の自動再開も未検証
5通知の上限（全体で1日20回・月100回、本番は200・2000）上限がサービス全体で1つだけ1人の長いラリーで全員の通知が止まる。人間関係ごとの上限がない
6会話の上限（12回の受け渡し、24時間）安全のための固定値ラリーの利用場面では短すぎることがある。Linkごとの設定にする
7配置（Renderのシンガポール）接続先（OpenAIの通知受け口、Cursorの api2.cursor.sh）の多くは米国にあると見込まれる呼び出しのたびに太平洋を往復する（1回あたり約0.1〜0.2秒の見込み、未計測）

2. 接続方式の比較

方式強み弱み判定
MCPでの中継（現行）ChatGPT・Grok・Muse・Claude・Pokeがみな「MCPを使う側」として対応している。今すぐ一般向けAIに届く唯一の共通の道Anybotsが中継に入る。起こす仕組みは各社でバラバラ（MCP Events・Webhook・なし）一般向けAIの主経路
A2A v1.0（Linux Foundation）名刺（Agent Card）・署名による身元確認・仕事の状態管理・ストリーミング・通知の受け口が標準化済み。主要クラウドが対応している相手がA2Aの受け口を持つ必要がある。一般向けAIは持っていない。人と人の関係や同意の仕組みは範囲外業務用・自作AIとの経路、外部への公開
直接通信（P2P）中継の遅延と費用がない一般向けAIは受け口を開けない。記録・停止・取り消しを保証できない将来：A2A同士で、許可の証明だけAnybotsが出す
Webhookで起こす（dots・Grok）止まっているAIを起こせる起動に15〜46秒かかる。各社の非公開仕様に依存する止まっている相手には必須
短い間隔での確認（Muse）何の仕組みもなく動く確認のたびにAIの1手。遅くて高い次の「待ち受け」に置き換える
待ち受け（来るまで応答を保留する）1回の呼び出しで「次のメッセージが来たら即座に返る」。確認の繰り返しが不要各社のツール呼び出しの制限時間に縛られる（未検証）動いているAI同士のラリーの主経路
ストリーミング（MCPの途中経過通知、A2AのSSE）相手の途中経過を即座に流せる対応状況が各社バラバラ対応している相手だけで使う
相手のチャットに直接送る（SMSやiMessageでPokeへ）APIがないAIにも届く利用規約、なりすまし、記録の点で危うい最後の手段。検証が先

判定：組み合わせ型にする。制御面（身元・Contact・Link・許可・記録・停止）は1つにまとめて、どの経路を使っても同じ判断と記録になるようにする。データ面は「起こす」「待ち受け」「A2A」「人へのお知らせ」の部品を相手ごとに選ぶ。

4. 超高速ラリーの設計

目標の時間

区間今目標手段
Anybots内（保存から相手に届くまで）最大1秒強＋ロック待ち（最悪10秒）50ms以下（中央値）保存した直後にその場で配送。全体ロックは廃止
動いているAI同士の1回の受け渡し2回の呼び出し、Museは5秒の確認AIが考える時間だけ（1回の呼び出し）「返信して次を待つ」
止まっているAIを起こす15〜46秒相手の会社しだい（短縮は不可）起こす回数を減らす：まとめて処理、構造化した依頼、ラリー中は起こしたまま

中心になるツールの形

inbox_claim({ conversation_id?, wait_s?: 0..25 })
  → { turnId, conversationId, message, ... } | null     // 来るまで保留して即座に返る。空振りはAIの1手を使わない

turn_finish({ turn_id, result, text?, expects_reply?, idempotency_key, next?: { wait_s? } })
  → { turnId, result, messageId?, next?: 受け取り | null }   // 返信と完了と、次の受け取りを1回で

実装では既存の inbox_claim に wait_s を足した。Grokのルーチンなど、今の指示文をそのまま使えるようにするため。送信と同時に返事を待つ conversation_open の待ち受けは、inbox_claim の待ち受けで代わりになるため作らない。

  • 受け取りと完了の2回を、完了と次の受け取りの1回にまとめる。ラリー中はどちらのAIも1往復ごとに1回のツール呼び出しで済む。
  • 待ち受けの最大時間は、各社のツール呼び出しの制限時間より短く設定する（初期値は25秒）。制限時間は実際に計測してから決める。途中経過の通知で呼び出しを延長できる相手には延長する。
  • 重複時の安全性（再送キー、期限、結果不明の扱い）は今の約束を保つ。

中継側の変更

変更中身得られるもの
外部送信中のロック解放全体ロックは短いトランザクションの中だけで使い、外部へのHTTP送信中には持たない。送信は「ロックの中で予約して確定 → ロックなしで送る → 結果を記録」の2段階にする。会話ごとのロックへの分割は、利用者が増えて計測で必要になってから行う遅い通知先が他の全員を止めない。ロックを持つ時間は1回あたり数ミリ秒
保存した直後の配送コミットした後、APIのプロセス内でその場で配送する。複数台で動かすときは LISTEN/NOTIFY で知らせる。再試行と取りこぼしの回収だけ、30秒ごとの見回りで行う1秒ごとの問い合わせとworkerサービス（月$7）が不要になる
待ち受けの合図待っている呼び出しには、プロセス内の待機と LISTEN/NOTIFY で即座に知らせるRedisは不要。部品は増やさない
本文を合図に入れる（選べる）署名付きの合図に本文と1回限りの受け取りチケットを入れて、相手が turn_finish だけ呼べば済むようにする。Linkごとに選べるようにし、セキュリティレビューと回帰試験を必須にする止まっている相手でも呼び出しが1回減る
構造化した依頼予定調整などは「空き時間の候補」を型付きのデータで渡す。何往復も文章でやりとりしない往復の回数そのものが減る。一番効く高速化
上限をLinkごとに通知の回数・受け渡しの回数・会話の期限を、Linkと持ち主ごとに設定する。全体の上限は費用の安全網として残す1人の暴走が全員を止めない
配置の見直し接続先の地域を計測してから、米国の地域への移設を判断する呼び出しのたびの往復時間が縮む

6. プロダクトの姿

立ち位置

誰もが自分のAIを持ち、AIが代わりに連絡・調整する社会では、「誰のAIに」「どこまで許して」「何が起きたか」を会社をまたいで中立に管理する層が必要になる。AI同士の通信方式はMCPとA2Aで標準化されていく。でも人と人の信頼関係と許可は、どのAI会社も中立にはやれない。Anybotsはそこを取る。AIアシスタントそのものとは競争しない。

中心になる考え方

単位意味今のテーブルとの関係
Person人。パスキー・Apple・Googleでログインするowners を発展させる。運営が発行する閲覧鍵（directory_credentials）は廃止
Agentその人のAI。提供元・表示名・アイコン・起こし方・最後に通信した時刻bindings に表示名と起こし方を足す
Contact人と人の関係（家族・友達・仕事）。両方の承認で成立する新規
Link私のAgent ↔ 相手のAgent。Contactの下にぶら下がるgrants を置き換える。運営の手作業ではなく、両者の同意で作る
PolicyLinkごとの許可・上限・静かな時間帯・期限新規
Thread / Receiptやりとりと、配達・既読・回答・承認の記録conversations・messages・turns・outbox を人が読める形で見せる

利用の流れ（ママのChatGPT ↔ 私のPoke）

  1. 登録：パスキーでログイン →「Add agent」→ Pokeを選ぶ → 接続の認証 → 接続テストが成功すると表示が「Connected」になる。
  2. 招待：「Invite family」→ リンクかQRコードをLINEやSMSで送る。
  3. ママの登録：リンクからログイン →「Add ChatGPT」→ ChatGPTのアプリ一覧からAnybotsを追加する（未検証）。
  4. 許可の合意：テンプレートを選ぶ（例：家族＝質問と予定調整は自動、実行と個人情報は毎回確認、22時〜7時は送らない）。両方が同じ条件を承認すると、Linkが有効になる。
  5. 使う：Pokeに「ママに日曜空いてるか聞いて」→ 許可を確認して届ける → ママのAIが受け取る。止まっていればママへお知らせ → 返事 → Pokeが私に伝える。
  6. 管理する：承認待ちの箱、Linkの一時停止と取り消し、タイムラインの確認と書き出し。

8. 許可と追跡

許可

段階は「質問・調整・実行」の3つで、それぞれ「自動・毎回確認・禁止」から選ぶ。初期値は関係ごとのテンプレートで決める。AIの画面の中での「はい」は許可とみなさない。人が自分の端末で承認した記録を残す（IETFのAI委任の草案と同じ考え方）。相手のAIの文章は命令ではなくデータとして扱う。

追跡

状態は「送信 → 配達 → 既読 → 回答／承認待ち／拒否／期限切れ」。両方の持ち主が同じ記録を見られる。「相手のAIが終わったと言った」ことと「実際に終わった」ことは分けて表示する。後で改ざんを検出できる形（ハッシュの連鎖）にする。

停止

Linkの一時停止・取り消し・Agentの切断は、どれもすぐ効く。すでに相手へ渡った本文や、相手が始めた操作は取り消せないことを画面で正直に示す。

身元

Agentごとに、Anybotsが署名したA2Aの名刺（Agent Card）を発行する。どの人の、どのAIかを相手に証明する。将来は本人確認の段階（電話番号、身分証）を選べるようにする。

    4. 企業のAIに、個人のAIから連絡できる「AI用の電話番号」（最大の市場）
  • 守りの強み：人と人の信頼関係のグラフ、許可の履歴、各社との接続の積み重ね、中立であること。
  • 入口の候補：家族の見守り（親に怪しい依頼が来たら子のAIにも知らせる）、友達の予定調整、@handle でAIに届く仕組み。
  • リスク：
    • OpenAIやAppleが同じものを作る → 会社をまたげることで差をつける
    • 一般向けChatGPTの制限
    • 起こせないAIが多いこと
    • 個人情報の法規制
    • AI同士のスパムや乗っ取り

10. MVPと段階計画

MVP「Family Link」

2人・2社のAI（PokeとChatGPT）で、3つの用途（予定調整・質問とリマインド・情報共有）が、許可と記録つきで動く状態。支払い、企業のAI、外部へのA2A公開、複数の端末は入れない。

成功の指標：

  • 招待した人が実際に登録してLinkができる割合
  • 1週間あたりの、違う会社のAI同士のやりとりの数
  • 動いているAI同士の1回の受け渡しの中央値（目標：AIが考える時間＋50ms以下）
  • 人が途中で何もせずに往復した割合

公開の前に決めておくこと（PR #26の提案から採用）：

  • 出荷の定義：運営ではない人が、運営のSSH・秘密ファイル・DB操作なしに招待から往復まで終え、その結果が画面に残ること。中継の記録だけが成功して画面に何も出ない場合は成功に数えない。
  • 試用の枠を分ける：公開の試用は、全体共通の通知上限（本番は1日200回）を食い合わない別の小さな枠で動かす。1人がたくさん使った日に全員が止まらないようにする。

10.5 2026-10-05の再確認：標準・既存の仕組み・競合・研究

結論：土台の方針（制御面を1つ、データ面は相手に合わせる）は変えない。最速でMVPを出すために足りないのは、新しい通信方式ではなく、①外向けの入口（LP）、②AIが「誰と話しているか」を分かること、③v0.2.0での実アカウントの往復の再確認、の3つ。

標準

対象2026-10時点の状況Anybotsの判断
A2A v1.0Linux Foundationで150以上の組織が支持。Agent CardのJWS署名（RFC 8785で正規化）、supportedInterfaces、Device Code・PKCE、マルチテナント一般向けAIは今もA2Aの受け口を持たないので、主経路はMCPのまま。A2Aの入口は段階5。Agent Cardを公開すると「誰がどのAIを使っているか」が漏れるため、公開カードには個人を載せず、つながった相手だけに拡張カードを見せる
MCP 2026-07-28とTasks拡張ツール呼び出しに長時間の仕事の識別子を返し、input_required で途中の入力を求められる承認待ち（approval='pending'）と同じ形。ChatGPT・Grokが対応したと確認できてから載せる（未検証）。今は wait_s の待ち受けで足りる

既存のオーケストレーション

LangGraph・CrewAI・AutoGen・OpenAI Agents SDK・Google ADKは、1人の持ち主の中で複数のAIを動かす仕組み。持ち主をまたぐ同意と取り消しは範囲外。2026年9月の研究では、このうち3つに権限の閉じ込めが組み込まれていなかった。競合ではなく、将来A2Aでつながる相手として扱う。

競合と近いプロダクト

名前やっていることAnybotsとの差
Instinct（評価額100億ドル）「信頼できる人のネットワーク」で、友達のInstinct同士が予定を合わせる自社のAIだけで閉じている
Pickle（iPhone、月$8.99）友達のPickle同士が会話し、持ち主を紹介する。共有範囲は持ち主が決める自社のAIだけ。利用者は今使っているAIを持ち込めない

共通点：資金も利用者も「AI同士が人の代わりに調整する」に集まっている。どれも自社のAIか同じ持ち主の中で閉じている。「今使っている違う会社のAIを持ち込み、持ち主どうしが許した範囲だけでつなぐ」は空いている。LPの主張はここに絞る。

研究

  • Delegation Without Trust：「AIが完全に乗っ取られても、委ねられた権限を超えられない」ことを正しさの基準にする。判定はAIの外で行う。Anybotsの方針判定は中継側で行うので、この基準に沿っている。intentは送る側の自己申告で、この点は残余リスクとして既に記録している。
  • マルチエージェントのプロンプトインジェクション：送り主の出どころを付ける（署名と追跡）と、AI間のインジェクションが91%減った。Anybotsでは、受け取ったメッセージに中継側が確認した送り主（Agent名と持ち主名）を付ける。本文の中の自称は信用しない。
  • IETFの委任チェーンの草案：A2Aで外部へ委ねるとき（段階5）の権限の縮小に使う候補。

MVPに足りないもの（優先順）

#足りないもの対応
1/ が404で、何のサービスか伝わる入口がない今回：/ にLPを置く（スクリプトなし、外部資源なし）
2agents_list がIDと提供元しか返さず、受け取ったメッセージに送り主の名前がない。「ママのAIに聞いて」を正しい相手に結べない今回：相手のAgent名・持ち主名・自分のAgentか・相手が受け付けるintentを返す。受け取りには、中継側で確認した送り主を付ける
3v0.2.0での実アカウントの往復が未確認利用者の再接続のあとに記録する
4最初の1人の招待にSSHが必要次の段階：運営向けのWeb招待
5起こせないAIの持ち主へのお知らせがない次の段階：メールかプッシュ通知
6デモ動画と、成功の指標の集計往復を確認したあとに撮る。status に指標の件数を足す

判定：1・2・3が揃えば、招待制のベータとして最速で出せる。一般公開（自己登録、課金、複数台構成）はMVPに入れない。
