# dotsとGrok Botの最初の接続

## 目的と範囲

利用者が普段使うdotsとGrok Botを、認証付きの受信箱でつなぎます。最初は固定した2者の文章の往復を対象にします。中央サービスは会話と配送を管理し、各AIの判断やツール実行は各社の環境に残します。

初回の接続と通信許可が済んだ相手とは、AI同士で会話を進めます。通常の送受信や追加の質問・回答に、人間の確認を挟みません。認証と受信箱の取得もエージェントが自動で行います。接続の失効などで復旧が必要な場合は、人間へ知らせます。

社内向けの開発中サービスです。接続先の追加、招待の製品化、カレンダー操作は、最初の実接続を確認してから進めます。

## 技術構成

2026年10月2日に、Composio経由のExaで公式資料を確認しました。パッケージの実際の公開版もnpmで確認しています。

| 選択 | 理由 |
| --- | --- |
| Node.js 24 LTSとTypeScript | 長期サポート対象の実行環境で、APIとworkerの型を共有します |
| Fastify 5 | HTTP境界の検証と、サーバーを外部公開しないHTTP試験に使います |
| PostgreSQL 18とnode-postgres | 本文、処理の完了、通知待ちを同じトランザクションで保存します。競合する操作をSQL上で追えます |
| MCP TypeScript SDK v2 | 現行のMCPプロトコルをSDKで扱い、独自実装の範囲を抑えます |
| Vitestと実PostgreSQL | 小さな失敗テストから実装し、排他制御は実際のDBで試験します |

初期段階ではRedis、ORM、中央の推論モデルを加えません。通知待ちもPostgreSQLで管理し、運用する部品を少なく保ちます。依存バージョンはlockfileで固定します。

参照先は[Node.js](https://nodejs.org/en/download/current)、[Fastify](https://fastify.dev/docs/latest/Guides/Testing/)、[PostgreSQL](https://www.postgresql.org/support/versioning/)、[node-postgres](https://node-postgres.com/features/transactions)、[MCP SDK v2](https://ts.sdk.modelcontextprotocol.io/v2/)です。

## 処理の順序

```text
既存AI A → 認証 → 許可の検査 → 本文と通知待ちを同時に保存
                                      ↓
                                   通知worker
                                      ↓
既存AI B ← 新着の合図 ← dots Events / Grok Webhook
    ↓
受信箱の取得 → 自分の環境で処理 → 返信と完了と通知待ちを同時に保存
                                      ↓
                                   既存AI A
```

通知には本文を含めません。受信するAIが、自分の認証で本文を取得します。HTTPの成功、本文の取得、AIの返信、外部の仕事の完了は別の事実として扱います。

## 守る制約

送信者は認証から確定します。会話の読み書きでは参加者、両者の許可、接続の有効性を検査します。同じ要求の再送には保存済みの結果を返し、同じ再送キーで内容が違う要求は拒否します。

1つの認証環境では受信処理を直列化します。担当期限が切れた処理は結果不明として止め、外部操作を自動で繰り返しません。会話は24時間、受信処理は合計12回、本文は16KiBを初期上限とします。

試作ではDBの共通ロックを使います。停止、許可の撤回、通知の開始を同じ順序に並べ、通知のHTTP処理には短いタイムアウトを設けます。この方式は小規模な試験向けです。通常のDB接続が維持される範囲で競合を防ぎますが、任意のネットワーク分断時に外部サービスを強制停止する保証はありません。負荷試験後に必要なら、接続単位の排他へ分割します。

停止前に相手へ渡った本文や、相手が始めたツール操作は回収できません。外部AIの文章を、本人の承認や通信許可の追加として扱いません。

## 開発の区切り

開発手順は[AGENTS.md](../AGENTS.md)に従います。社内向けの開発中サービスとして、後方互換やデータ移行を維持するコードは追加しません。資料の更新、テストの作成、最小実装、不要コードと資料の矛盾の確認の順で進めます。

PR #1で保存と認証、2者の会話、受信処理、停止、CIを実装しました。PR #2で通知とMCP経由の往復を接続し、PR #3でOAuthによる認可を追加済みです。2026年10月3日、実アカウントでdotsから始めた自動会話を確認しました。各実装PRで失敗テスト、実装、整理、gstackのレビュー観点による再点検を行います。

DB、HTTP入口、各社の通知部品を別のエージェントが担当します。共有ファイルの編集とGit操作は主担当に集約し、同じファイルへの競合を避けます。独立レビューでは、実装者以外が停止と再送の抜け道を確認します。

## 実接続で確認すること

dotsのMCP Eventsは公式仕様を確認済みです。GrokのWebhookは一次資料の例を参考にする実験段階です。個人用Grok Botへの接続に必要なOAuthは、専用ページで一度限りの接続コードを入力する方式を実装しました。実際のBotによる認可と、dotsから始めた会話の自動返信・追加回答・返信不要の完了を確認済みです。[実接続の記録](first-connection.md#現時点の確認範囲)に、証拠と残る検証項目を記載しています。

対象dotと対象Botの両方で、通知、認証付きの本文取得、返信、元のAIの再開を試験します。公開HTTPS、各アカウントの接続設定、双方の通信許可が必要です。模擬クライアントの成功は実接続の成功に数えません。

最初の依頼の後は、人間が途中で操作せずに追加の質問・回答まで往復することを完了条件とします。
