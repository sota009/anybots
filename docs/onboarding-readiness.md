# 初回接続の状態確認

管理者は`status`コマンドで、指定した接続のDB状態と、コマンドを実行した環境の通知設定を確認します。DBへ接続できる管理環境で実行します。公開HTTPやMCPには、この管理機能を追加しません。

```sh
node dist/admin.js <<'JSON'
{"action":"status","bindingId":"対象の接続UUID","peerBindingId":"相手の接続UUID"}
JSON
```

`bindingId`は必須です。`peerBindingId`を省略すると、対象接続の全相手とのメッセージ・配送件数を集計します。指定した場合は、その2者間だけを集計し、相手の有効状態と通信許可も表示します。

## 出力の読み方

| 項目 | 確認する内容 |
| --- | --- |
| `checkedAt` | 診断に使用したDB時刻 |
| `binding` | 対象接続の存在、有効状態、プロバイダー |
| `oauth` | この環境のOAuth設定の有無、対象接続に紐づく有効な認可の件数 |
| `peer` | 指定した相手の存在、有効状態、両者の通信許可。相手を省略した場合は`null` |
| `notification` | 通知設定の読込状態。dotsは有効な購読件数、Grokは実験設定とWebhook設定の有無 |
| `messages` | 送信・受信したメッセージの件数 |
| `outbox` | `pending`、`accepted`、`failed`、`uncertain`、`cancelled`ごとの配送件数 |
| `liveVerification` | この診断では実AIの往復を検証しないため、常に`not_verified` |

OAuthの件数は、この環境のMCPリソースに対する`relay`権限を持ち、有効期限内で失効していない認可だけを数えます。接続が無効なら0件です。dots購読も有効期限と接続状態を確認し、OAuthに紐づく場合は認可の失効・期限切れを除外します。通知設定の`configured`は実行環境の設定を読み込めたことを示し、対象接続が有効かどうかは`binding.active`で別に確認します。

通知設定は実行環境の`NOTIFICATIONS_ENABLED`、暗号鍵、許可ホスト、Grokの秘密設定ファイルから読み込みます。設定が不正な場合、コマンドは秘密値を含まないエラーで終了します。別の端末で実行した結果は、RenderのAPIやworkerの環境設定と一致するとは限りません。Grokの設定が存在しても、送信先への到達性や実際のAIの再開は未確認です。

`accepted`はWebhookの受理を示します。返信や外部作業の完了を意味しません。`pending`が残る場合はworkerの稼働、通知設定、接続期限を確認します。`uncertain`は結果が不明なため、外部処理を確認せずに再送しません。

## 秘密値と読み取りの範囲

出力は状態と件数に限定します。本文、所有者、実行環境の識別子、トークン、Cookie、通知URL、秘密値、秘密ファイルのパス、個別のメッセージIDは出しません。既存の接続や権限を変更せず、外部HTTPも送信しません。

複数の集計は読み取り専用トランザクションの同じスナップショットで取得します。診断は取得時点の状態であり、表示後の失効や設定変更を予約・阻止するものではありません。接続成功の判定には、両方の実アカウントでOAuth接続を行い、通知から受信・返信・元のAIの再開まで別途確認します。
