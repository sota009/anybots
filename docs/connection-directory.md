# 利用者向け接続一覧

2026年10月4日。社内の限定試験向け。所有者に登録されたAI接続と直結相手を、読み取り専用で確認する。

## 判断と到達点

最初に作ったのは、自分の接続と直結相手を確認する読み取り専用CLIと、同じ認可・応答モデルの一覧APIである。続けて、同一オリジンの読み取り専用Web UIを追加する。導入は運営が支援し、利用者はDBやSSHを扱わない。

ページ分割とローカル別名は初版から外す。限定試験では「全件を一度で取得できるか、取得できなかったと明示するか」を優先する。本文の暗号化や高速な会話とは独立して進める。この機能は本文を読わず、AIを起動しない。接続関係は私的情報として扱い、現行の本文平文保存や外部AIの操作権限までは解消しない。

| 含める | 後の段階 |
| --- | --- |
| 運営支援の所有者登録、閲覧資格情報の発行・失効 | 一般向け自己登録、ログイン基盤、組織・共有所有 |
| 自分の接続一覧、直結相手、登録状態、許可の記録 | 友達追加・解除、接続の登録・削除を利用者が行う機能 |
| 一つの接続への絞り込み、JSON出力、同一オリジンWeb UI | 別名の編集、公開プロフィール、履歴・本文 |
| macOSターミナルとブラウザからの一度取得 | Windows専用配布、監視・ポーリング |
| 所有者ごとの情報分離と読み取り試験 | 個別AIの所有証明、オンライン診断、自動往復の新たな検証 |

## 正規モデル

```text
owners.id（人の管理主体）
    ├── directory_credentials（一覧専用の鍵）
    └── bindings.owner_id（登録時に決める所有者）
             └── grants（どの接続と通信できるか）
```

| 保存対象 | 初版の契約 |
| --- | --- |
| `owners` | ランダムUUIDの`id`、`directory_enabled`、作成時刻。メールや外部アカウント名で識別しない |
| `bindings.owner_id` | `owners.id`へのNOT NULL外部キー。1接続の所有者は1人。任意文字列のownerは正規モデルに残さない |
| `directory_credentials` | UUID、所有者FK、秘密のSHA-256ハッシュ、固定スコープ`directory:read`、環境のaudience、発行時刻、期限、失効時刻 |
| `grants` | 既存の接続ペアとactive。自分同士でも自動許可しない |

スコープとaudienceはサーバーが検査する。期限は発行から最大24時間。失効済み資格情報は再有効化しない。未失効の資格情報は所有者ごとに1つまで。再発行は所有者行をロックした一つのトランザクションで旧資格情報の失効と新資格情報の登録を行う。

`directory_enabled=false`は一覧へのアクセスを止める。会話停止とは別。無効化時は所有者行ロック下で全閲覧鍵も失効させる。所有者の付け替え、共有所有、物理削除は初版に含めない。

`delivery_attempts.owner_id`も`owners.id`へ揃え、表示機能の追加で利用枠が別人へ合算されたり予算検査を迂回したりしないことを回帰試験する。

後方互換とデータ移行は作らない。正規スキーマは新しい空DBで作り、既存の任意文字列ownerを補正する互換層は置かない。

## 運営支援での登録

1. 本人と対応が取れる認証済みの社内連絡経路で登録依頼を受け、所有者UUIDを発行する。AIの文章や自己申告ラベルだけでは発行しない。
2. 新しい接続は作成時にその所有者へ固定する。claim機能はない。
3. 外部サービスとの認証は接続ごとに行う。個別AIの本人確認バッジには転用しない。
4. 運営が利用者のmacOSアカウントにCLIと一覧専用資格情報を配置する。DB資格情報、SSH鍵、運営用CLIは渡さない。
5. 利用者が`anybots connections`を実行し、登録控えと一致することを確認する。

## 閲覧鍵

暗号学的乱数32バイトから、接続用とは異なる種類の秘密を作る。サーバーへ送るのはハッシュと資格情報ID。秘密は利用者の保護ファイルにだけ配置し、チャット・メール・チケット・標準出力へ貼らない。

既定配置は`~/.config/anybots/directory.json`。親ディレクトリ0700、ファイル0600、所有UID一致、通常ファイル、`O_NOFOLLOW`と開いたFDの`fstat`で確認する。任意試験は`--credentials <ファイルパス>`。秘密を引数や環境変数で渡す機能は作らない。

CLIは配布時に固定したHTTPS originだけへ送る。任意の`--url`、HTTP降格、TLS検証無効、リダイレクト追跡は認めない。自動延長やrefresh tokenはない。紛失・漏えい時は運営が資格情報IDを失効させ再発行する。

## 一覧API

```text
GET /v1/me/connections
GET /v1/me/connections?connection_id=<自分の接続UUID>
Authorization: Bearer <一覧専用の秘密>
```

Fastifyの独立ルートに一覧専用認証を登録する。`/mcp`用フックを全ルート共通にはしない。Cookie、接続用OAuth、静的な接続用トークンは受け付けない。CORSは初版では開放しない。機能フラグで既定無効とし、対応スキーマと設定が揃った試験環境だけで有効にする。

成功応答の要点:

- `schemaVersion: 1`、`checkedAt`（サーバーの取得開始時刻）、`complete: true`のみが全件成功
- `connections[]`は対象接続のUUID順、相手もUUID順
- `registration`は`active|disabled`
- 許可がactiveの相手だけを返す。自分または相手の登録が無効なら`registrationAllowsCommunication=false`
- `sameOwner`がfalseの相手の所有者ID、名前、メール、他の接続は返さない
- 本文、`runtime_scope`、生の`owner_id`、ハッシュ、認可コード、通知先URL、秘密値、最終活動時刻は含めない

上限: 自分の接続最大100件、相手の行合計1,000件、UTF-8 JSON最大1 MiB。超過は一覧を返さず422 `inventory_too_large`。件数だけ切り詰めた200は返さない。

認証・所有者有効性・所有確認・一覧読み取りは一つの`REPEATABLE READ READ ONLY`トランザクションで行う。`Relay.run`、`sweep`、受信箱claim、外部呼び出し、会話用グローバルロックは通さない。一覧ハンドラーの応答とローカル処理は3秒で打ち切る。認可結果や一覧はキャッシュしない。

| 状況 | HTTPとコード |
| --- | --- |
| 秘密なし・無効・期限切れ・失効、一覧停止 | 401 `unauthorized` |
| 有効だがスコープ不足 | 403 `forbidden` |
| 未知／他人の接続 | 404 `connection_not_found` |
| UUID形式不正、未知・重複クエリ | 400 `invalid_request` |
| 上限超過 | 422 `inventory_too_large` |
| 要求過多 | 429 `rate_limited` |
| DB停止・待ち超過・内部失敗 | 503 `unavailable` |

401には一覧用の`WWW-Authenticate: Bearer`を付け、MCP用OAuthへ誘導しない。すべての応答へ`Cache-Control: no-store`。エラー本文は固定コードと要求IDのみ。

## CLI契約

```text
anybots connections
anybots connections --connection <自分の接続UUID>
anybots connections --json
```

HTTPは1回だけ、8秒で打ち切る。自動再試行しない。終了コード: 0成功、2引数・資格情報ファイル、3が401/403、4が400/404/422、5が429/503・通信・応答検査失敗。`--json`のstdoutは成功時のJSONのみ。stderrは固定エラーコードと次の行動だけ。秘密・生HTTP・例外は出さない。

## 資源制限

一覧専用DBプールは最大2接続、入場待ち最大8要求、待ち上限500ms、各SQLのstatement timeout 1秒、lock timeout 250ms。プロセス内制限は入口全体毎分120・burst 20、認証済み所有者ごと毎分60・burst 10。所有者枠は認証前の自己申告や無効トークンでは減らさない。一覧は業務DBを変更しない。通知予算やAI利用枠を消費する経路は設けない。

索引: `bindings(owner_id,id)`、`grants`の両端からactiveな相手を引ける索引。接続を101件、相手行を1,001件まで取得して超過判定し、上限内の小さい結果だけをアプリ側でUUID順に並べる。N+1照会や全件走査はしない。

## Web UI

`DIRECTORY_ENABLED=true` のときだけ、同一オリジンで `GET /directory` を公開する。APIと同じ機能フラグに従い、既定無効を維持する。CORSは開放しない。Cookie・接続用OAuth・MCPトークンは使わない。閲覧秘密はブラウザの `sessionStorage` にだけ置き、サーバーへ永続化しない。ページを閉じると消える。

UIは既存の `GET /v1/me/connections` を1回呼び、同じDTOとエラーコードを表示する。自動再試行しない。本文・秘密・通知先URLをDOMやログへ出さない。CSPは `default-src 'none'` を基本に、同一オリジンの script/style と必要なフォント配信だけを許可する。

## 実装単位

| PR | 内容 | 試験 |
| --- | --- | --- |
| P1 所有者と閲覧鍵 | 正規スキーマ、発行・失効の運営経路、秘密ファイル配置 | T1/T2/T9の秘密ファイル（実装済み） |
| P2 認可済み一覧 | 独立HTTPルート、read-only照会、DTO、負荷制限。既定無効 | T3〜T7（ローカル実装済み） |
| P3 CLIと統合 | 配布物、引数、出力、エラー、初回導入資料 | T8/T9/T10（ローカル実装済み。実利用者の初回実行は未確認） |
| P4 Web UI | 同一オリジンの読み取り専用画面、sessionStorage資格情報、CSP | ルート既定無効、DTO描画、401/422表示、秘密非表示 |

完了報告は「設計完了」「ローカル試験合格」「隔離環境の導入合格」「実際の所有者の一覧確認」を分ける。模擬データの成功を実アカウントの成功と呼ばない。部分PRのマージを機能公開と扱わず、一覧ルートの既定無効を維持する。

## 残る境界

- 本番切り替え時の対象環境、旧データの保持・破棄、再認証・購読再設定の手順と了承は未確定。隔離環境での実装・試験は進められるが、この判断前に本番へ切り替えない。
- 一般公開のログイン基盤、複数端末、個別AIの所有確認、ページ分割は対象外。
- 運営を信頼する社内試験であり、運営の誤登録まで暗号学的に防ぐ設計ではない。
